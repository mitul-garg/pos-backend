JPA entities rather than written by hand, these docs are the only human-readable

## How the schema is produced

Generated by Hibernate from entity annotations (`hbm2ddl`). **There is no
migration tool** — the deploy strategy is drop-and-recreate rather than migrate,
so there's no data to preserve across a schema change, which is the only thing
Flyway would buy. (Revisit if the deployed database ever holds data worth keeping.)

| Environment | `hbm2ddl.auto` |
|---|---|
| Tests | `create-drop` — the schema always matches the entities exactly and can't drift |
| Local dev | `update` |
| Deployed | `create` on first boot, then `validate` so divergence fails fast at startup |

Two consequences worth internalising:

- **Declare every constraint and index explicitly** in `@Table(uniqueConstraints
  = …, indexes = …)`. Hibernate will not invent them, and there is no `.sql` file
  where someone would notice they're missing.
- **`validate` checks tables and columns only — never indexes or unique
  constraints.** Nothing in the stack will ever tell you a unique key failed to
  materialise. That's why `SchemaConstraintsIT` queries `information_schema` for
  the isolation-critical ones.

A generated `schema.sql` is committed alongside the code so DDL changes show up in
diffs and get reviewed. **Regenerate and commit it whenever an entity changes** —
it's most of what a migration tool gives you, for one config property.

## Conventions

**Naming** — `snake_case` tables and columns, singular table names. `order` and
`return` are SQL reserved words, so the tables are **`pos_order`** and
**`sales_return`**. Constraints are named explicitly (`uk_…`, `idx_…`, `fk_…`); a
constraint you can't name is one you can't reference in an error message.

**Keys** — `BIGINT AUTO_INCREMENT` surrogate primary keys, **globally unique, never
per-tenant**. That's what lets a cross-tenant fetch miss cleanly instead of
colliding with another tenant's row. Ids are serialized to JSON as **strings**, so
the frontend's existing string comparisons keep working.

**Money** — `DECIMAL(12,2)`, mapped to `BigDecimal`. Never `DOUBLE`, never `FLOAT`.
An invoice cannot carry float artefacts.

**Timestamps** — `DATETIME(6)`, UTC, named `created_at`.

**Booleans** — `BOOLEAN` (`TINYINT(1)`), `NOT NULL` with an explicit default.

**Enums as `VARCHAR`**, not MySQL `ENUM` — adding a value to a MySQL `ENUM` is a
table alter, and `hbm2ddl.auto=update` won't perform it. Values are validated in
the application layer.

## The two rules that shape every table

**1. `tenant_id NOT NULL` on every tenant-owned table.**

Including `order_line` and `return_line`, which are reachable only through their
parent. That's mild denormalisation, taken deliberately: it lets the Hibernate
filter apply uniformly to every entity, so no table depends on a *join* being
scoped correctly to stay safe. Each table is independently isolated.

**2. Uniqueness is `(tenant_id, …)`, never global — except `tenant.code`.**

`(tenant_id, username)`, `(tenant_id, sku)`, `(tenant_id, qr_code)`,
`(tenant_id, order_number)`, `(tenant_id, return_number)`. Two stores legitimately
both have an `admin`, a `BISLERI-1L`, and an `ORD-2026-0001`. A schema that
rejects those has a global constraint where a per-tenant one belongs.

`tenant.code` is the single globally-unique field — it's the login discriminator.

## The reserved platform tenant

`SUPER_ADMIN` users belong to a **reserved `platform` tenant row** rather than
having `tenant_id = NULL`.

The reason is concrete: **MySQL treats NULLs as distinct in a unique index**, so
`UNIQUE(tenant_id, username)` would place *no constraint at all* on platform users
— you could insert ten `superadmin` rows and MySQL would accept every one. The
alternative fix is a generated column, which Hibernate can't emit from annotations.
A reserved row keeps `tenant_id NOT NULL` everywhere and lets the plain composite
key do its job.

This is a **storage detail, not a wire contract**: the API still reports
`tenantId: null` for platform users, matching the frontend's model of a
`SUPER_ADMIN` belonging to no tenant. The row is flagged `is_platform = TRUE`, is
excluded from `GET /api/tenants`, and cannot be suspended.
